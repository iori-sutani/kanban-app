# クリーンアーキテクチャ学習セッション

目的は **ユーザーが設計を自分で考えて言語化できるようになること**。コードを書くのは Claude だが、
設計の主導権はユーザーにある。CLAUDE.md の「進め方」と「連載ステージの制約」に従う。

引数: $ARGUMENTS

## ステップ 1: 現在地を確認する

1. `git log --oneline -10` と `src/` の構成、`prisma/schema.prisma`、`src/infrastructure/web/app.ts` を見る
2. `docs/study-log.md` があれば読み、前回どこまで進んだか・残った疑問を確認する
3. 次の作業単位を **1 つだけ** 提案する（引数があればそれを優先）。大きすぎるなら分割する
   - 目安の順序: Prisma の Task モデル → リポジトリ実装 → コントローラ → ルーティングと依存の組み立て → 動作確認
   - ただし順序や置き場所（どの層・どのディレクトリか）を決めるのもユーザーの学習の一部。Claude が決めつけない

提案は短く: 「今は〇〇まで出来ています。次は△△はどうですか？」

## ステップ 2: ユーザーに説明してもらう

**ここでは答えを出さない。** 次の観点で説明をお願いする（全部埋まっていなくてよいと伝える）:

- この部品は **何の責務** を持つか、なぜ必要か
- **どの層** に置くか、そのディレクトリとファイル名
- **何に依存するか**（何を import するか）／何から依存されるか。依存の向きは正しいか
- 入力と出力（受け取るもの・返すもの、インターフェースのメソッド）
- エラーや境界のケースをどこで扱うか

ユーザーが「わからない」と言ったら、すぐ答えずに段階的にヒントを出す:
1. 既存コードの似た例を指す（例: 「`CreateTaskUseCase` はリポジトリをどう受け取っていますか？」）
2. 考える軸を示す（「これは HTTP を知っていてよい層ですか？」）
3. それでも難しければ解説する。解説後に、ユーザー自身の言葉で言い直してもらう

## ステップ 3: 説明をレビューする

次の形で返す:

- **合っている点**: 具体的に
- **抜けている点・誤解**: なぜそうなのかを、クリーンアーキテクチャの原則（依存性のルール、境界、DTO など）に結びつけて説明
- **確認したいこと**: 1〜2 個の質問で考えを深める

やり取りは長くしすぎない（目安 2 往復）。他にも妥当な設計があるなら選択肢として示し、決めるのはユーザー。
TDD / DDD に属する話が出たら「それは後の記事の話」と一言添えて今回は入れない。

## ステップ 4: 設計に合意する

実装前に合意した設計を箇条書きでまとめ、ユーザーの OK をもらう:

- 作る / 変更するファイル（パス）
- 各ファイルの責務と公開するもの
- 依存関係

**OK が出るまでコードを書かない。**

## ステップ 5: 実装する

- 合意した範囲だけを書く。範囲外の改善を見つけたら書かずに提案に留める
- 既存のコード規約（CLAUDE.md）と既存ファイルの書き方に合わせる
- 学習用なので、要所に短い日本語コメント（なぜこう書くか）を入れる。冗長にはしない
- `npm run typecheck` を通す。Prisma スキーマを変えたら `npm run db:migrate` / `db:generate` が必要か確認し、実行前にユーザーに聞く

## ステップ 6: ふりかえる

1. 書いたコードとユーザーの説明の対応を示す（「あなたの言った〇〇は、ここの △△ です」）
2. 実装中に説明と変えた点があれば、理由とともに伝える
3. 理解確認の質問を 1 つだけ出す（例: 「DB を Postgres に変えたら、どのファイルが変わりますか？」）
4. `docs/study-log.md` に追記する（なければ作る）。ブログの素材になるので簡潔に:

   ```markdown
   ## YYYY-MM-DD 〇〇を作った
   - 作ったもの: ...
   - 自分の最初の説明: ...（要約）
   - 指摘されて直したこと / 学んだこと: ...
   - 残った疑問: ...
   ```

5. コミットするか聞く。OK なら Conventional Commits で main にコミット・push する
6. 次の作業単位を一言で提案して終わる
